\section{Analysis and Comments}
\label{sec:analysis}
\subsection{Time and Space Complexity}

separately. The standard-library version uses lazy deletion and may retain $O(m)$

For the Fibonacci heap, all arc scans and successful decrease-key operations total
$O(m)$, and each vertex is involved in at most one effective extract-min, for a
total of $O(n\log n)$. On sparse graphs, this bound has the same order as that of a
binary heap, but each Fibonacci-heap operation maintains more links, so the
asymptotic difference does not necessarily yield a smaller constant.

The analysis of the radix heap relies on bucket indices decreasing during
redistribution. If the largest valid key is bounded by $U$, then
$B=\lceil\log_2(U+1)\rceil$. The specialized radix design in the literature yields
an $O(m+n\log C)$ bound for Dijkstra's algorithm, where $C$ is the edge-weight upper
bound \cite{radix}. The present implementation uses 32 buckets and compressed
handles and does not exactly match all assumptions of that design, so the tighter
bound is not adopted here.

This study did not collect peak-memory curves, hardware cache counters, the number
of successful relaxations, or the number of bucket redistributions. The space
analysis follows from the data structures and is not a measured memory result.

\subsection{Observed Performance of the Fibonacci Heap}
The NY and BAY road networks have average out-degrees of only about 2.78 and 2.49,
respectively, and are therefore sparse. The Fibonacci heap reduces the asymptotic
cost of decrease-key, but it must still consolidate roots of equal degree, maintain
linked lists, and perform cascading cuts. Although the nodes are allocated
contiguously in an array, each operation follows node links, whereas most binary-heap
state resides in compact arrays. More frequent link updates and poorer locality may
explain part of the gap. This is an inference from the implementation structure and
would require operation counts and performance-counter data to evaluate. No metrics
that directly distinguish cache misses were collected.

In the dense family, edge scanning grows with $n^2$ and heap maintenance may account
for a smaller fraction of the total time, reducing some gaps between queues. The
largest dense case in this study has only $n=4096$, which is insufficient to determine
the eventual winner at large scale. Although the random graphs reach larger vertex
counts, their sparsity is entirely different, so they cannot substitute for
large-scale dense experiments.

\subsection{Differences between the Radix Heap and SPFA}
On nonnegative-integer road networks, the radix heap exploits the monotonicity of
keys and avoids much of the sift-up and sift-down work in comparison heaps. It is the
fastest of the seven Dijkstra queues in this study. It still requires valid key
ranges and sufficient handle capacity, so it cannot directly replace a general
priority queue for real-valued or non-monotone keys.

SLF+LLL is faster than every heap implementation on both networks, while FIFO SPFA is
more than an order of magnitude slower. Changing only the scheduling order of SPFA
thus changes performance substantially. The two implementations also use different
memory strategies, duplicate entries versus an in-queue marker, so their gap cannot
be attributed solely to SLF or LLL. Good performance on the random graphs does not
guarantee efficiency on adversarial inputs.

\subsection{Model Fitting and Measurement Limitations}
\plotfigure{complexity-normalized}{CPU time normalized by the prescribed models. The curves are not strictly constant; the figure is intended only to show model deviation and finite-size effects.}{fig:normalized}
The complexity plots record timings at a finite set of discrete sizes. Changes in a
normalized curve may come from the algorithm's operation count or from caching,
compilation, clock frequency, or input reachability. A small RMS indicates only that
the model fits the observed range; it does not rule out another model or establish a
tight bound.

Three repetitions of the random and complexity experiments are insufficient to
estimate tail behavior reliably. The road networks have only one batch and no
per-query distribution, and the two network sizes are insufficient for a reliable
scaling fit. WSL shares the host hardware, and CPU affinity and host load were not
controlled, so absolute times serve only as a reference for this run.

\subsection{Further Improvements}
Further work should add independent road-network batches and per-query records, as
well as larger graph sizes. It should also record the numbers of relaxations,
outdated entries, root consolidations, and bucket redistributions, together with
performance-counter data that can explain constant-factor costs. For true
point-to-point queries, the implementations should first apply a common
target-termination rule before introducing bidirectional search or preprocessing
algorithms.

The amortized bounds did not determine the observed ordering. On the sparse road
networks, the theoretical advantage of the Fibonacci heap did not translate into
speed, while the radix heap and suitably scheduled SPFA were faster. This ordering
remains specific to the present inputs and implementations.
